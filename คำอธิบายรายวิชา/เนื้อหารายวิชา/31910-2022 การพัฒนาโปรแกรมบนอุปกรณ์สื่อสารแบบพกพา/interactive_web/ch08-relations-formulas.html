1. สถาปัตยกรรมความสัมพันธ์แบบตารางแม่-ลูก (Parent-Child / Header-Detail)

1.1 ความล้มเหลวของแนวคิด "ตารางเดี่ยว" (The Single Table Fallacy)

ในระบบธุรกิจดิจิทัลแทบทุกประเภท ไม่ว่าจะเป็นแอปพลิเคชันช็อปปิ้ง (Shopee, Lazada), แอปสั่งอาหาร (GrabFood, LINE MAN), หรือระบบบริหารจัดการองค์กร ข้อมูลหนึ่งรายการมักจะมี "รายการย่อย" ประกอบอยู่เสมอ หากผู้พัฒนาพยายามบันทึกข้อมูลคำสั่งซื้อทั้งหมดลงในตารางเดียว ดังตัวอย่าง:

❌ ตัวอย่างโครงสร้างที่ผิดพลาด: ตารางเดี่ยวแบบบันทึกแถวยาว (Anti-Pattern)

ORD-002 วิภา รักเรียน อเมริกาโน่ 1 null (ว่าง) null (ว่าง) null (ว่าง) null (ว่าง)
  • โครงสร้างตารางขยายตัวอย่างไร้ขีดจำกัด: หากลูกค้าสั่งสินค้า 15 รายการ ระบบจะไม่สามารถรองรับได้จนกว่าเราจะเพิ่มคอลัมน์ด้วยมือไปถึง Menu_15
  • ข้อมูลกระจัดกระจายและสูญเปล่า (Sparse Data): ลูกค้าที่สั่งเพียงแก้วเดียวจะปล่อยให้คอลัมน์ที่เหลือว่างเปล่า สิ้นเปลืองพื้นที่ฐานข้อมูล
  • ไม่สามารถวิเคราะห์ข้อมูล (BI & Reporting): ไม่สามารถใช้คำสั่งหาผลรวมยอดขายแยกตามรายสินค้าได้โดยตรง

1.2 วิธีที่ถูกต้อง: สถาปัตยกรรมแม่-ลูก (Header-Detail Structure)

ในวิศวกรรมฐานข้อมูลสากล ความสัมพันธ์ระหว่าง "ใบคำสั่งซื้อ 1 ใบ" กับ "รายการสินค้าหลายรายการ" จัดเป็นความสัมพันธ์แบบ หนึ่ง-ต่อ-กลุ่ม (1-to-Many Relationship) จึงต้องแยกข้อมูลออกเป็น 2 ตารางที่เชื่อมโยงกันด้วยคีย์อ้างอิง:

1. ความยืดหยุ่นของจำนวนสินค้า จำกัดตามจำนวนคอลัมน์ที่ตั้งไว้ล่วงหน้า ไม่จำกัด ลูกค้าจะสั่ง 1 รายการ หรือ 100 รายการก็ได้
2. การใช้พื้นที่จัดเก็บ (Storage) สิ้นเปลือง เกิดช่องว่าง Null จำนวนมาก มีประสิทธิภาพสูง จัดเก็บเฉพาะแถวที่มีรายการจริง
3. การคำนวณและสรุปผล (Analytics) สูตรซับซ้อนมาก ไม่สามารถรวมยอดขายรายสินค้าได้ง่าย ใช้สูตร SUM / COUNT ได้ตรงไปตรงมา สรุปรายงานได้ทุกมิติ
4. ความถูกต้องของประวัติราคา หากเปลี่ยนราคาสินค้า อาจกระทบบิลเก่าได้ง่าย รักษาราคาประวัติศาสตร์ระดับแถว (Historical Price Integrity)
5. ประสบการณ์ผู้ใช้บนหน้าจอมือถือ (UX) ฟอร์มยาวเหยียด เลื่อนหน้าจอยาก มีช่องว่างรบกวนสายตา ฟอร์มกระชับ มีปุ่มกดเพิ่มสินค้าแบบ Inline Subform สวยงาม
6. ความเข้ากันได้กับมาตรฐานสากล ผิดหลักการ Normalization (1NF Violated) ถูกต้องตามมาตรฐาน Relational Database (3NF)
หน่วยที่ 2 (AppSheet Relational Engine)

2. ชนิดข้อมูล Ref และพลังวิเศษของคุณสมบัติ IsPartOf

ใน AppSheet ตัวเชื่อมโยงระหว่างตารางเรียกว่าชนิดข้อมูล Ref (Reference) ซึ่งแตกต่างจาก Text ธรรมดา เพราะเมื่อกำหนดคอลัมน์ใดเป็น Ref แล้ว AppSheet จะรับรู้ความสัมพันธ์เชิงความหมายทันที โดยระบบจะสร้างลิงก์คลิกนำทาง (Deep Navigation) และอนุญาตให้เขียนสูตรดึงข้อมูลข้ามตารางได้อย่างง่ายดาย

TXT

ชนิดข้อมูล Text ธรรมดา

เป็นเพียงตัวอักษรเรียงกัน เช่น "ORD-1001" ระบบไม่รู้ว่าข้อความนี้มีความหมายถึงแถวไหนในระบบ ไม่สามารถคลิกเพื่อเปิดดูรายละเอียด และไม่สามารถดึงข้อมูลของตารางนั้นมาคำนวณได้

REF

ชนิดข้อมูล Ref (Foreign Key)

เก็บกุญแจหลัก (Primary Key) ของอีกตารางหนึ่ง กลายเป็น Hyperlink อัจฉริยะ นำทางผู้ใช้ไปยังข้อมูลต้นทางได้ทันที และเปิดความสามารถในการเขียนนิพจน์แบบ Dereference เพื่อดึงฟิลด์ต่างๆ ข้ามตารางได้ทันที

2.1 เจาะลึก 3 พลังวิเศษเมื่อเปิด IsPartOf = TRUE

เมื่อตั้งค่าคอลัมน์ Order_ID ในตารางลูก Order_Details ให้เป็น Ref ชี้ไปยัง Orders จะมีตัวเลือกหนึ่งที่ต้องติ๊กถูกเสมอ นั่นคือ:

✓ IsPartOf = TRUE (คอลัมน์นี้เป็นส่วนหนึ่งที่แยกขาดไม่ได้ของตารางแม่)

การติ๊กเครื่องหมายถูกนี้จะกระตุ้นพฤติกรรมอัตโนมัติ 3 ประการที่เป็นหัวใจของแอปพลิเคชันธุรกรรม:

1

Embedded Inline Subform (หน้าจอสั่งซื้อแบบมีตะกร้าสินค้าในตัว)

เมื่อผู้ใช้กดสร้างบิลในหน้า Orders ด้านล่างของฟอร์มจะมีส่วนตารางแสดงรายการสินค้าพร้อมปุ่ม [+ Add / + New] ปรากฏขึ้นมาอัตโนมัติ ผู้ใช้สามารถกดเพิ่มสินค้า เลือกกาแฟ ปรับจำนวน และเห็นตะกร้าสินค้าได้ทันทีโดยไม่ต้องกดออกจากฟอร์มแม่

2

Cascade Delete (กลไกลบตามกัน ป้องกันข้อมูลขยะกำพร้า)

หากในอนาคตผู้จัดการสั่งลบบิลคำสั่งซื้อ ORD-1001 ออกจากระบบ รายการสินค้าทั้ง 5 รายการในชีต Order_Details ที่ผูกติดกับบิลนี้จะถูกลบตามไปด้วยทันที ป้องกันไม่ให้เกิดเรกคอร์ดกำพร้า (Orphan Records) ค้างอยู่ในชีต

3

Auto-generated Virtual Column (คอลัมน์เสมือนอัตโนมัติ [Related...])

AppSheet จะสร้างคอลัมน์เสมือนในตารางแม่ให้โดยอัตโนมัติในชื่อ [Related Order_Details] ซึ่งเก็บข้อมูลเป็น List of Refs ของแถวลูกทั้งหมดที่ตรงกับ Order_ID นี้ ทำให้เราสามารถนำไปเขียนสูตรคำนวณ Rollup ต่อได้ทันที

ข้อพึงระวังเชิงสถาปัตยกรรม: เมื่อใดที่ไม่ควรเปิด IsPartOf = TRUE?

ห้ามเปิด IsPartOf ในความสัมพันธ์ประเภทที่ไม่ใช่ความเป็นเจ้าของแท้จริง เช่น ความสัมพันธ์ระหว่าง Orders ➔ Customers (หากเปิด เมื่อลบบิลคำสั่งซื้อ ลูกค้าจะถูกลบทิ้งไปด้วย!) หรือ Products ➔ Categories (หากเปิด เมื่อลบหมวดหมู่ สินค้าทั้งหมดจะหายไป!) ดังนั้น IsPartOf = TRUE ต้องใช้เฉพาะตารางลูกที่เกิดมาเพื่อบิลนั้นๆ เท่านั้น

หน่วยที่ 3 (Business Expressions & Calculations)

3. การดึงราคาอัตโนมัติด้วย Dereference และการคำนวณมูลค่าย่อยในแถว

3.1 ไวยากรณ์ Dereference: การวิ่งข้ามตารางในบรรทัดเดียว

ในการบันทึกคำสั่งซื้อ เมื่อพนักงานหรือลูกค้าเลือกสินค้าจากเมนู Dropdown เช่น เลือก [PROD-01: ชานมไต้หวัน] เราไม่ควรให้ผู้ใช้ต้องมานั่งจำหรือพิมพ์ราคาต่อแก้วเอง เพราะจะทำให้เกิดความผิดพลาดในการกรอก (Human Error)

AppSheet มีกลไกที่เรียกว่า Dereference Expression ซึ่งช่วยให้เราสามารถชี้ทะลุคอลัมน์ Ref ไปยังตารางปลายทางได้ทันทีด้วยเครื่องหมายจุด .

ไวยากรณ์ Dereference พื้นฐาน: AppSheet Expression
[ชื่อคอลัมน์_Ref].[ชื่อคอลัมน์ในตารางเป้าหมายที่ต้องการดึง]
ตัวอย่างใช้งานจริงในช่อง Unit_Price: =[Product_ID].[Price]

3.2 กฎเหล็ก: ใส่สูตรใน Initial Value หรือ Formula?

คำถามที่พบบ่อยที่สุดในหมู่นักพัฒนา AppSheet คือ: "ควรใส่สูตร =[Product_ID].[Price] ไว้ในช่อง Initial Value หรือในช่อง Formula?"

คุณสมบัติ Initial Value (ค่าเริ่มต้นตอนเปิดฟอร์ม) ✅ ถูกต้องสำหรับราคา Formula (สูตรคำนวณตลอดชีพ) ❌ ผิดสำหรับราคา
การทำงาน ดึงค่ามาใส่ให้ ครั้งแรกเพียงครั้งเดียว ตอนเริ่มสร้างแถวใหม่ คำนวณใหม่ ตลอดเวลา เมื่อมีการบันทึกหรือซิงก์ข้อมูล
การแก้ไขตัวเลข ผู้ใช้สามารถปรับลดราคา หรือใส่ราคาพิเศษได้ตามสิทธิ์ กลายเป็น Read-Only (ผู้ใช้ไม่สามารถแก้ไขได้เลย)
ผลเมื่อร้านขึ้นราคาสินค้าในอนาคต บิลเก่ายังคงราคาเดิม (50 บาท) ไม่ถูกแก้ตาม รักษาประวัติการขายถูกต้อง (Historical Integrity) บิลเก่าของเดือนที่แล้วจะถูกเปลี่ยนราคาตามสินค้าปัจจุบันทันที! ทำให้ยอดบัญชีย้อนหลังเพี้ยน

3.3 การคำนวณมูลค่าย่อยในแต่ละแถว (Row Subtotal)

ที่คอลัมน์ Subtotal ในตารางลูก Order_Details เราต้องการให้คูณยอดเงินอัตโนมัติจากจำนวนชิ้นและราคาต่อหน่วย:

สูตรในช่อง Formula ของคอลัมน์ Subtotal: Read-Only Real-time
=[Quantity] * [Unit_Price]
กำหนดประเภทข้อมูล Type = Price (สกุลเงิน THB / ฿) และทศนิยม 2 ตำแหน่ง

3.4 ตารางเปรียบเทียบเชิงลึก: Dereference vs LOOKUP() vs SELECT()

AppSheet มีฟังก์ชันสำหรับดึงข้อมูลข้ามตาราง 3 รูปแบบหลัก ซึ่งมีข้อดีและข้อจำกัดที่วิศวกรซอฟต์แวร์ต้องเลือกใช้ให้ตรงกับบริบท:

รูปแบบคำสั่ง ตัวอย่างไวยากรณ์ ความเร็ว (Performance) เงื่อนไขและข้อแนะนำ
1. Dereference [Product_ID].[Price] เร็วที่สุด (O(1)) ต้องเป็นคอลัมน์ Ref เท่านั้น เป็นตัวเลือกอันดับหนึ่งที่แนะนำเสมอ
2. LOOKUP() LOOKUP([_THISROW].[Product_ID], "Products", "Product_ID", "Price") ปานกลาง (O(N)) ใช้เมื่อคอลัมน์ไม่ได้ตั้งเป็น Ref หรือต้องการค้นหาแบบ Dynamic ในตารางอื่น
3. SELECT() ANY(SELECT(Products[Price], [Product_ID] = [_THISROW].[Product_ID])) ช้าที่สุด (Table Scan) ส่งผลลัพธ์เป็น List เหมาะกับการกรองเงื่อนไขซับซ้อนหลายชั้น ไม่ควรใช้กับแถวจำนวนมาก
สูตร LOOKUP() มาตรฐาน
=LOOKUP([_THISROW].[Product_ID], "Products", "Product_ID", "Price")
สูตร SELECT() กรองเฉพาะเจาะจง
=SUM(SELECT(Order_Details[Subtotal], [Order_ID] = [_THISROW].[Order_ID]))
หน่วยที่ 4 (Rollup Aggregation Patterns)

4. การรวมยอดเงินสุทธิด้วย Rollup Aggregation Patterns

เมื่อตารางลูก (Order_Details) มีการคำนวณราคารวมย่อยในแต่ละแถวแล้ว ขั้นตอนสุดท้ายที่สำคัญที่สุดของระบบสั่งซื้อคือการรวบรวมตัวเลขเหล่านั้นกลับขึ้นมาแสดงผลเป็น "ยอดรวมทั้งสิ้น (Grand Total)" และ "จำนวนรายการสินค้าทั้งหมด" ในตารางแม่ (Orders)

รูปแบบนี้เรียกว่า Rollup Aggregation Pattern ซึ่งอาศัยฟังก์ชันทางคณิตศาสตร์ทำงานร่วมกับคอลัมน์เสมือน [Related Order_Details]

SUM EXPRESSION สูตรคำนวณยอดเงินรวมทั้งสิ้น (Grand Total)
=SUM([Related Order_Details][Subtotal])
1. SUM(...)
ฟังก์ชันคณิตศาสตร์ หาผลรวมตัวเลขทั้งหมดที่อยู่ในลิสต์
2. [Related Order_Details]
คอลัมน์เสมือนที่รวบรวมทุกแถวของบิลนี้มาไว้เป็นกลุ่ม
3. [Subtotal]
ระบุว่าจะดึงเฉพาะคอลัมน์ Subtotal ของทุกแถวมาประมวลผล
นับจำนวนรายการสินค้าในบิล:
=COUNT([Related Order_Details][Detail_ID])

นับจำนวนแถวในตารางลูกที่ผูกกับบิลนี้ เหมาะสำหรับทำข้อความระบุ เช่น "บิลนี้มี 3 รายการ"

นับจำนวนชิ้นสินค้ารวมทั้งหมด:
=SUM([Related Order_Details][Quantity])

นำตัวเลขในช่อง Quantity ของทุกแถวมารวมกัน เช่น สั่ง 2 แก้ว + 3 แก้ว = รวม 5 ชิ้น

ทำไมเราจึงสร้าง Total_Amount เป็น Virtual Column ใน AppSheet แทนที่จะสร้างคอลัมน์ใน Google Sheets?

➔ วิธีแก้: ไปที่ Data > Columns > ตารางลูก (เช่น Order_Details) > คลิกรูปดินสอที่ Order_ID > ติ๊กถูกช่อง "IsPartOf" แล้วกด Save
⚠️ ปัญหาที่ 2: ช่อง Unit_Price ว่างเปล่า ไม่ดึงราคาอัตโนมัติเมื่อเลือกสินค้า สูตร Dereference

สาเหตุ: สะกดชื่อคอลัมน์ผิด หรือคอลัมน์สินค้ายังไม่ได้ตั้งเป็น Ref ชี้ไปยังตาราง Products

➔ วิธีแก้: ตรวจสอบว่า Product_ID เป็น Ref ชี้ไปที่ Products จริง แล้วใส่สูตรในช่อง Initial value: =[Product_ID].[Price]
⚠️ ปัญหาที่ 3: ช่อง Total_Amount ขึ้น Error เครื่องหมายตกใจสีเหลือง หรือได้ 0.00 Rollup Error

สาเหตุ: พิมพ์ชื่อตารางลูกในสูตร SUM ไม่ตรงกับชื่อคอลัมน์เสมือนที่ AppSheet สร้างขึ้นมา

➔ วิธีแก้: เปิดดูในตารางแม่ มองหาคอลัมน์ประเภท List ที่ขึ้นต้นด้วย "Related..." เช่น =SUM([Related Order_Details][Subtotal])
⚠️ ปัญหาที่ 4: เมื่อเปลี่ยนราคาสินค้าในตาราง Products ยอดเงินในบิลเก่าถูกเปลี่ยนตาม ประวัติราคาผันแปร

สาเหตุ: นำสูตร =[Product_ID].[Price] ไปใส่ไว้ในช่อง Formula แทนที่จะใส่ใน Initial value

➔ วิธีแก้: ลบสูตรออกจากช่อง Formula แล้วนำมาวางในช่อง Initial value ของคอลัมน์ Unit_Price เพื่อรักษาราคาประวัติศาสตร์
⚠️ ปัญหาที่ 5: แอปแจ้งเตือน Circular Reference Warning สูตรวนลูป

สาเหตุ: มีการอ้างอิงสูตรข้ามไปมาระหว่างแม่กับลูกแบบวนรอบไม่รู้จบ

➔ วิธีแก้: ตรวจสอบให้แน่ใจว่าตารางลูกอ้างอิงตารางแม่ทางเดียว และตารางแม่อ้างอิงตารางลูกเฉพาะในขั้นตอน Rollup SUM เท่านั้น
⚠️ ปัญหาที่ 6: ผู้ใช้ใส่จำนวนติดลบ หรือใส่ 0 ได้ ทำให้ยอดเงินติดลบ Data Validation

สาเหตุ: ไม่ได้กำหนดกฎตรวจสอบเงื่อนไขในคอลัมน์ Quantity

➔ วิธีแก้: ไปที่คอลัมน์ Quantity ในช่อง Valid_If ใส่สูตร: [_THIS] > 0

11. คำถามทบทวนประจำบท (Review Questions & FAQ Accordion)

คลิกที่แต่ละคำถามเพื่อเปิดดูคำอธิบายทางวิชาการและการนำไปใช้ในงานจริง:

คำตอบทางวิชาการ: เพราะความสัมพันธ์ระหว่างคำสั่งซื้อกับสินค้าเป็นแบบ 1-to-Many (1 ใบสั่งซื้อมีได้ตั้งแต่ 1 ถึงหลายสิบรายการ) หากรวมในตารางเดียว เราจะไม่รู้ว่าต้องสร้างคอลัมน์ Menu_1 ถึง Menu_เท่าใด ทำให้ตารางขยายตัวอย่างไร้ระเบียบ เกิดข้อมูลว่างเปล่า (Sparse Nulls) สิ้นเปลืองพื้นที่ และไม่สามารถนำข้อมูลไปทำรายงานสรุปยอดขายแยกรายสินค้าได้ การแยกตารางแม่-ลูกจึงเป็นมาตรฐานสากล (3NF Normalization) ที่มีประสิทธิภาพสูงสุด
คำตอบทางวิชาการ: ส่งผล 3 ด้านหลัก: (1) ด้าน UX ทำให้หน้าจอสร้างบิลแม่มีฟอร์มฝังตัว (Embedded Inline Subform) ผู้ใช้สามารถกด [+ New] เพื่อเพิ่มสินค้าลงตะกร้าได้ทันทีในหน้าจอเดียว, (2) ด้านความปลอดภัย ป้องกันข้อมูลกำพร้าด้วย Cascade Delete หากลบบิลทิ้ง รายการสินค้าของบิลนั้นจะถูกลบทิ้งอัตโนมัติ, และ (3) ด้านสูตร AppSheet จะสร้างคอลัมน์เสมือน [Related...] ให้โดยอัตโนมัติเพื่อใช้คำนวณ Rollup SUM
คำตอบทางวิชาการ: เพื่อรักษา ความถูกต้องของประวัติราคาในอดีต (Historical Price Integrity) หากใส่ใน Formula เมื่อร้านกาแฟปรับขึ้นราคาสินค้าจาก 50 เป็น 65 บาทในเดือนหน้า บิลเก่าทั้งหมดที่ขายไปเมื่อเดือนที่แล้วจะถูกเปลี่ยนราคาเป็น 65 บาทตามไปด้วย ทำให้ยอดขายย้อนหลังเพี้ยนทันที แต่การใส่ใน Initial Value จะดึงราคามาบันทึกไว้ในแถวนั้นอย่างถาวรเพียงครั้งเดียว บิลเก่าจึงยังคงราคา 50 บาทตามจริง
คำตอบทางวิชาการ: Dereference [Ref].[Target] เร็วที่สุด (O(1)) เพราะใช้ Pointer วิ่งตรงไปยัง Foreign Key จึงเป็นตัวเลือกแรกเสมอเมื่อมีคอลัมน์ Ref, ส่วน LOOKUP() เหมาะเมื่อไม่มีคอลัมน์ Ref แต่ต้องการค้นหาค่าจากตารางอื่น, และ SELECT() มีประสิทธิภาพช้าที่สุดเพราะต้องสแกนค้นหาทั้งตาราง เหมาะสำหรับการกรองข้อมูลที่มีเงื่อนไขซับซ้อนหลายชั้นเท่านั้น
คำตอบทางวิชาการ: หากใช้ =COUNT([Related Order_Details][Detail_ID]) จะเป็นการนับจำนวนรายการแถว (เช่น สั่งชานม กับ ครัวซองต์ จะได้ 2 รายการ) แต่ถ้าต้องการผลรวมชิ้นจริง (เช่น ชานม 2 แก้ว + ครัวซองต์ 3 ชิ้น = 5 ชิ้น) ต้องใช้สูตรหาผลรวมคอลัมน์ Quantity นั่นคือ: =SUM([Related Order_Details][Quantity])
