Agile Scrum Framework & Sprint 1

System Integration Pattern

ประยุกต์ใช้สถาปัตยกรรม System Integration Pattern เพื่อรวบรวมโมดูลทั้งหมด (UI, Database, Relations, Actions, Hardware, Maps, Automation) เข้าเป็นระบบเดียวที่ไร้รอยต่อ

Minimum Viable Product (MVP 80%)

1. กระบวนการ Agile Scrum และการวางแผน Sprint 1

ตลอด 12 สัปดาห์ที่ผ่านมา นักศึกษาได้เรียนรู้ทักษะเชิงเทคนิคทีละโมดูลอย่างเป็นขั้นตอน แต่ในโลกการทำงานจริงระดับองค์กร ซอฟต์แวร์ระดับมืออาชีพไม่ได้ถูกสร้างจากบุคคลคนเดียว แต่เกิดจาก "ทีมวิศวกรซอฟต์แวร์และนักวิเคราะห์ธุรกิจ" ที่ร่วมมือกันส่งมอบงานเป็นรอบระยะสั้น ๆ เรียกว่า Sprint

คำศัพท์สำคัญ (Scrum Terms) ความหมายเชิงปฏิบัติการ บทบาทในรอบ Sprint 1 (Capstone Week 13)
Sprint Goal เป้าหมายสูงสุดประการเดียวของรอบการทำงานที่ทั้งทีมต้องทำให้สำเร็จร่วมกัน ส่งมอบแอปพลิเคชันเวอร์ชัน Beta (ความสมบูรณ์ 80%) ที่กดทำงานตั้งแต่ต้นจนจบได้จริงโดยไม่พัง
Definition of Done (DoD) ข้อตกลงและเกณฑ์ขั้นต่ำร่วมกันว่า "งานแบบไหนจึงจะเรียกว่าเสร็จสมบูรณ์" มีข้อมูลสินค้าจริงครบถ้วน, คำนวณเงินถูกต้อง, สแกนติด, เซ็นชื่อได้, แผนที่ขึ้น และบอทส่งอีเมล PDF สำเร็จ
Daily Standup Meeting การยืนประชุมสั้น ๆ ไม่เกิน 5 นาทีระหว่างสมาชิกในทีมเพื่อสื่อสารความคืบหน้า ตอบคำถาม 3 ข้อ: 1) ทำอะไรเสร็จไปแล้ว? 2) วันนี้จะทำอะไรต่อ? 3) ติดอุปสรรค (Blocker) ตรงไหนหรือไม่?
Sprint Backlog รายการการทำงานย่อย (Tasks) ที่ทีมดึงมาจาก Product Backlog มาลงมือทำใน Sprint นี้ การ์ดงานที่กระจายให้สมาชิก 3 คนรับผิดชอบบนกระดาน Kanban แบ่งเป็น Data, Frontend, QA
กฎเหล็ก 3 ข้อของการประชุม Daily Standup 5 นาที (ทีม 3 คน) Timeboxed: 5 Mins Max
คำถามที่ 1: ผลงานที่สำเร็จ
"เมื่อคาบที่แล้ว หรือช่วงเวลาที่ผ่านมา สมาชิกแต่ละคนประกอบโมดูลใดเสร็จสิ้นแล้วบ้าง?"
คำถามที่ 2: แผนงานเป้าหมายถัดไป
"ในอีก 1 ชั่วโมงข้างหน้า สมาชิกแต่ละคนจะหยิบการ์ดงานใดบน Sprint Backlog ไปทำต่อ?"
คำถามที่ 3: ปัญหาที่ติดขัด (Blockers)
"มีสูตรไหนที่คำนวณไม่ตรง บอทตัวไหนไม่ยอมทำงาน หรือมีสิ่งใดที่ต้องให้เพื่อนช่วยแก้หรือไม่?"

3. การตัดแต่งฟีเจอร์ตามหลัก MVP (Minimum Viable Product)

ในกระบวนการทำ Capstone Project นักศึกษาหลายกลุ่มมักตกหลุมพรางด้วยการ "อยากทำฟังก์ชันเยอะเกินไป (Feature Creep)" จนทำให้ระบบไม่เสร็จสักอย่าง ในรอบ Sprint 1 เรายึดหลัก กฎ 80/20 (Pareto Principle): การมุ่งเน้นสร้างฟีเจอร์เพียง 20% ที่สร้างคุณค่าทางธุรกิจหลักให้แก่ผู้ใช้งานได้ถึง 80%

✅ สิ่งที่ "ต้องมี" ใน Sprint 1 (Must-Have 80%) DoD Required
  • ✓ แคตตาล็อกสินค้าพร้อมรูปภาพจริง: ข้อมูลสินค้า/บริการไม่น้อยกว่า 10-15 รายการ มีภาพคมชัดและจัดหมวดหมู่เรียบร้อย
  • ✓ ระบบตะกร้าและสูตรคำนวณเงิน: เพิ่มสินค้าหลายชิ้น คำนวณ Subtotal และ Grand Total ถูกต้อง 100%
  • ✓ ปุ่มสเตท Action ควบคุมขั้นตอน: เปลี่ยนสถานะจาก Pending ➔ Paid ➔ In-Service ➔ Delivered
  • ✓ ฮาร์ดแวร์สแกนกล้องและลายเซ็น: สแกน Barcode/QR Code ติด และมีช่อง Signature สำหรับเซ็นรับรองบนหน้าจอ
  • ✓ แผนที่นำทาง GPS: ปักหมุดพิกัดจัดส่งและแตะปุ่ม Action เปิด Google Maps ได้จริง
  • ✓ บอทสร้าง PDF และส่งอีเมล: สั่งพิมพ์ใบเสร็จหรือใบนัดหมายลงโฟลเดอร์ Google Drive
⏳ สิ่งที่ "ยกยอดไป Sprint 2" (Nice-to-Have / UAT) Sprint 2 Scope
  • • ระบบคูปองส่วนลดหลายเงื่อนไขซับซ้อน: เช่น ซื้อ 3 แถม 1, โค้ดส่วนลดตามวันเกิด (ยกยอดไปทำใน Sprint 2)
  • • แดชบอร์ดสถิติและกราฟวิเคราะห์ยอดขายขั้นสูง: ให้เน้นที่ระบบการทำธุรกรรมหลัก (Core Transactions) ให้เสร็จก่อน
  • • การเชื่อมต่อระบบ Payment Gateway สด: เช่น บัตรเครดิตหรือพร้อมเพย์ API แบบเรียลไทม์ (ใช้ปุ่มจำลองการจ่ายเงินแทน)
  • • การตกแต่งเอฟเฟกต์แอนิเมชันหวือหวา: ให้เน้นที่ความเรียบง่าย สะอาดตา และความเร็วในการตอบสนองของแอปพลิเคชัน
คู่มือปฏิบัติการเชิงลึกแยกตามประเภทธุรกิจ

10. ข้อผิดพลาดที่พบบ่อยในการบูรณาการระบบ (Integration Pitfalls)

ในขั้นตอนการประกอบโมดูลย่อยเข้าด้วยกัน มักเกิดข้อผิดพลาดทางเทคนิคที่ทำให้ระบบสะดุด ตารางต่อไปนี้สรุปอาการของปัญหา สาเหตุที่แท้จริง และแนวทางแก้ไขระดับวิศวกรรม:

อาการผิดปกติ (Error Symptoms) สาเหตุที่แท้จริง (Root Cause) วิธีการแก้ไขระดับวิศวกรรม (Engineering Fix)
1. แอปโหลดช้ามากเมื่อเปิดบนมือถือ อัปโหลดไฟล์ภาพสินค้าความละเอียดสูงเกินไป (ขนาด 4K หรือไฟล์เกิน 5MB ต่อภาพ) ทำให้ดาวน์โหลดไม่ทัน ➔ บีบอัดภาพสินค้าให้ความกว้างไม่เกิน 1,000px และขนาดไฟล์ไม่เกิน 300KB ก่อนอัปโหลดลง Google Drive
2. บอทไม่ทำงานเมื่อกดสั่งซื้อบนมือถือ เงื่อนไขใน Event Trigger ของ Bot ตั้งค่าไว้ไม่ตรงกับค่าข้อความที่ปุ่ม Action ทำการบันทึกลงไป (เช่น พิมพ์ผิดตัวพิมพ์เล็ก-ใหญ่) ➔ ตรวจสอบค่าในคอลัมน์ Order_Status ว่าค่าที่ปุ่มส่งมาตรงกับเงื่อนไข [Order_Status] = "Paid" ทุกตัวอักษร
3. รายการสินค้าในตารางลูกไม่ยอมแสดงผล ค่า Foreign Key ในตารางลูก (Order_ID) หลุดหาย หรือไม่ได้เปิดใช้งานคุณสมบัติ IsPartOf ➔ ตรวจสอบว่าคอลัมน์ Order_ID ใน Order_Details เป็นชนิด Ref ไปยัง Orders และได้ติ๊กเลือก IsPartOf = TRUE
4. ยอดรวม Grand Total ไม่อัปเดตทันที ใช้สูตรใน Google Sheets แทนที่จะใช้ Virtual Column หรือสูตรคำนวณภายใน AppSheet Formula ➔ ย้ายสูตรมาคำนวณที่ AppSheet ในช่อง App Formula ด้วยคำสั่ง SUM([Related Order_Detailss][Subtotal])
5. กล้องสแกนเนอร์ไม่ยอมเปิดขึ้นมา แอปพลิเคชันยังไม่ได้รับสิทธิ์การเข้าถึงฮาร์ดแวร์กล้อง (Camera Permission) บนสมาร์ตโฟน ➔ เข้าสู่การตั้งค่าสมาร์ตโฟน เลือก AppSheet และเปิดอนุญาตให้เข้าถึง "กล้องถ่ายภาพ" (Allow Camera Access)
คลังเครื่องมือวิศวกรรมความต้องการ (Requirements Artifacts)

ให้นักศึกษานำรูปแบบแม่แบบการเขียนข้อกำหนดตามมาตรฐาน Agile Scrum ไปปรับใช้ในโครงงานของกลุ่มตนเอง พร้อมปุ่มคัดลอกในคลิกเดียว:

ในฐานะ [ผู้ใช้งาน: เช่น ลูกค้า / พนักงานหน้าร้าน / เจ้าหน้าที่ครุภัณฑ์] ฉันต้องการ [ความต้องการ: เช่น สแกนบาร์โค้ดสินค้าเข้าตะกร้าโดยไม่ต้องพิมพ์ค้นหา] เพื่อที่จะ [คุณค่าทางธุรกิจ: เช่น ลดเวลาในการสร้างคำสั่งซื้อลงเหลือไม่เกิน 5 วินาทีต่อรายการ]
แม่แบบที่ 2: เกณฑ์การยอมรับแบบ Given-When-Then (Gherkin Format)
สถานการณ์ (Scenario): การชำระเงินและออกใบเสร็จ PDF อัตโนมัติ กำหนดให้ (Given): คำสั่งซื้อมีสถานะเป็น "Pending" และมียอดเงินรวมถูกต้อง เมื่อ (When): ผู้ใช้งานแตะปุ่ม Action "[รับชำระเงิน]" บนหน้าจอ ดังนั้น (Then): สถานะคำสั่งซื้อจะเปลี่ยนเป็น "Paid" ทันที และระบบ Automation จะส่งใบเสร็จ PDF เข้าสู่อีเมลของลูกค้าภายใน 10 วินาที
แม่แบบที่ 3: สูตร AppSheet Grand Total คำนวณยอดเงินรวมทั้งบิล
SUM( SELECT( Order_Details[Subtotal], [Order_ID] = [_THISROW].[Order_ID] ) )

14. คำถามที่พบบ่อยประจำบทเรียน (Frequently Asked Questions)

รวมข้อสงสัยเชิงเทคนิคในการพัฒนาโครงงาน Sprint 1 พร้อมคำอธิบายเชิงลึกจากอาจารย์ผู้สอน:

เพราะตามหลักการของ Agile & MVP ในรอบแรกเราต้องการ "ซอฟต์แวร์ที่ใช้งานได้จริง (Working Software)" เพื่อทดสอบว่ากระบวนการทางธุรกิจหลัก (Core Pipeline) ทำงานได้โดยไม่สะดุด หากเราทุ่มเวลาทำฟีเจอร์ย่อยให้ครบ 100% เช่น คูปองซับซ้อน หรือกราฟสถิติ แต่ฟังก์ชันการสั่งซื้อหลักยังพัง โครงงานจะล้มเหลว ความสมบูรณ์ 80% จะถูกนำไปรับฟีดแบ็กจริงใน Sprint 2 (UAT) เพื่อขัดเกลาสู่ 100% ต่อไป
แอปจะเริ่มช้าลงหากจำนวนแถวในตารางเกิน 10,000 แถว หรือมีรูปภาพความละเอียดสูงมากเกินไป แนวทางป้องกันคือ: 1) ปรับขนาดภาพไม่เกิน 1,000px ก่อนบันทึก 2) ใช้ Security Filters ใน AppSheet เพื่อดึงเฉพาะคำสั่งซื้อของเดือนปัจจุบันหรือสถานะที่ยังไม่ปิดบิลมาแสดงผลบนสมาร์ตโฟน และ 3) หลีกเลี่ยงการใส่สูตร Google Sheets ในชีตหลัก ให้ใช้ Virtual Column ของ AppSheet แทน
AppSheet Version History เก็บประวัติโครงสร้างการตั้งค่าของแอป เช่น ฟอร์ม สูตร แอ็กชัน และบอท ส่วน Google Sheets Version History เก็บประวัติเนื้อหาและแถวข้อมูลในสเปรดชีต ทั้งสองส่วนแยกจากกัน จึงควรตั้งชื่อเวอร์ชันใน Google Sheets ควบคู่ไปกับการจดหมายเลขเวอร์ชันของ AppSheet ทุกครั้งก่อนเริ่มประกอบระบบใหม่
ตามหลัก Agile เมื่อเกิด Blocker ทีมต้องไม่ปล่อยให้เพื่อนร่วมทีมติดขัดตามลำพัง สมาชิกอีก 2 คนควรหยุดงานย่อยของตนชั่วคราวเพื่อทำ "Pair Programming (การช่วยกันแก้ปัญหาเป็นคู่)" ในการไล่ตรวจสูตรหรือสิทธิ์การเข้าถึงทันที เพื่อให้ท่อข้อมูลกลับมาไหลต่อเนื่องได้โดยเร็วที่สุด
ให้เข้าไปที่เมนู Manage ➔ Monitor ➔ Automation Monitor ใน AppSheet เพื่อดู Log บันทึกข้อผิดพลาด จุดที่ผิดบ่อยที่สุดคือ: 1) เงื่อนไขใน Event ไม่ตรงกับค่าที่แก้ไข 2) แอปยังอยู่ในสถานะ Prototype ทำให้ส่งอีเมลได้เฉพาะอีเมลของผู้สร้างแอปเท่านั้น (ต้องเพิ่มอีเมลผู้รับใน White-list หรือทดสอบด้วยอีเมลของตนเองก่อน)
การทดสอบรายโมดูล (Unit Testing) ตรวจสอบแค่ว่าฟังก์ชันนั้นกดแล้วทำงานหรือไม่ แต่ End-to-End User Journey ตรวจสอบว่า "ผู้ใช้งานจริงสามารถดำเนินชีวิตการทำงานตั้งแต่เปิดแอป สแกน สั่งซื้อ เซ็นชื่อ นำทาง และรับใบเสร็จได้ต่อเนื่องโดยไม่ต้องขอความช่วยเหลือจากโปรแกรมเมอร์หรือไม่" ซึ่งเป็นการพิสูจน์คุณค่าทางธุรกิจที่แท้จริง
